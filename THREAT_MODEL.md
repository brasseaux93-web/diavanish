# Threat model

Diavanish is for dialogue where the most dangerous facts are what was said and who met whom. This document says plainly what is protected, from whom, and where the protection stops.

## Actors

| Actor | Can | Cannot (by design) |
|---|---|---|
| Server operator / host | Read the database, watch memory and traffic, run modified code | Read chat or caucus messages; learn room keys; forge a facilitator's role signature or sender certificate; swap a participant's key without that browser refusing the room; inject or alter a chat line without it showing as unverified |
| Network observer | See that a device talks to the Diavanish server, and when | Read content (TLS plus E2EE) |
| Another participant | Read the floor chat they are admitted to | Read another seat's caucus; read messages from before they were admitted under an older key, or after they were removed; post on the floor under another seat's name or the facilitator's without the line showing as unverified |
| Facilitator | Read everything in their rooms, admit and remove seats, certify any signing key under any seat name | Pretend a ledger entry was approved by a seat that did not approve it (the ledger is hash-chained and sealed) |
| Subpoena or seizure of the server | Obtain the ledger, outcome summaries, accounts and hashed invites | Obtain chat, drafts, room keys or IP logs, because they do not exist on disk |

## Key flow

1. The facilitator's browser makes a room signing key (ECDSA P-256) and, for each key epoch, a room key and one caucus key per seat (AES-256-GCM).
2. Each participant's browser makes an ECDH P-256 key pair (to receive keys) and an ECDSA P-256 key pair (to sign chat) and uploads only the public halves.
3. The facilitator's browser wraps the room key for each admitted seat (ephemeral ECDH, then HKDF-SHA-256, then AES-GCM, bound to `room|seat|epoch`) and signs the wrap over the seat's public-key hash, which it computes itself.
4. The participant's browser unwraps the key, checks the signature against its own key hash, and shows a safety code derived from the room code and the facilitator's signing key. If the signature fails, the browser refuses the key. Because every wrap is signed by that key, a swapped room key is already refused; the code's job is to catch a swapped signing key, so it stays the same when the room key rotates and only changes (with a warning) if the facilitator's signing key does.
5. The facilitator's browser issues a sender certificate for each seat: a signature with its signing key over a versioned message binding the room code, the seat id, the seat's name as the facilitator's screen shows it, and the SHA-256 of the seat's signing key, which it computes itself. The server relays certificates; each browser verifies them against the facilitator key it unwrapped.
6. Every chat line carries the sender's seat id (or `facilitator`) and a signature over the channel, epoch, seat id, name, text and send time. The facilitator signs with its own signing key. Receivers check the line against the certificate for that seat, show the name from the certificate rather than the message, and mark any line that fails, lacks a signature, or replays an earlier signature as "Unverified sender". Such lines are shown, not hidden, so tampering is visible.
7. The facilitator's browser starts a new epoch with a fresh room key and fresh caucus keys when a seat is removed or banned, and whenever the current epoch is older than 30 minutes (`EPOCH_MAX_AGE_MS` in `shared/e2ee.ts`). Browsers keep earlier epoch keys in memory for scrollback until the tab closes; a seat admitted later never receives them.

## Known limits

- **The facilitator's device is the root of trust.** Whoever controls it can read every message in its rooms. Use a dedicated, updated device.
- **The served code must be honest.** A web app is only as trustworthy as the JavaScript it receives. A malicious host could serve code that leaks keys. Mitigations: self-host, pin a reviewed release, and check the server against its published build hashes. Every build writes `/build-manifest.json` (a SHA-256 of each file the browser receives, plus one root hash); CI fails if two clean builds differ; tagged releases publish the manifest and `SHA256SUMS`; and `npm run verify -- https://host` rebuilds locally and re-hashes every file the server actually sends. This catches a host serving different code at the time you check. It cannot stop a host that serves honest code to the checker and different code to one participant; a browser extension or native client that checks on every load would close that gap.
- **Safety codes only help if people compare them.** The code catches a swapped facilitator signing key, which every wrap and sender certificate depends on. It is useful only when it is read aloud on a separate channel, such as in person or by phone.
- **The server could withhold a seat's key instead of swapping it.** In that case the participant sees "waiting for key" and nothing is exposed, but the server can deny service. If a facilitator's wrap goes to a substituted key, the server learns the room key, and the real participant's browser shows a key error. Treat any key error as a reason to stop and rotate.
- **Sender signatures are only as honest as the facilitator.** Per-sender signatures stop one seat (or the server) posting as another, but a malicious or compromised facilitator device can certify any key under any name, or sign lines as itself. Signatures also do not hide who said what from the facilitator, and a seat can still deny nothing: a signed line is attributable to that seat's key for as long as someone keeps the plaintext. A seat whose tab is compromised can be impersonated with its own key. Lines without a valid signature are shown as unverified, not dropped, so a reader must notice the label. The server only serves certificates for seats that are currently admitted, so a browser that joins after a seat has left (or after it reopened on a new device with a new signing key) shows that seat's earlier lines as unverified.
- **Traffic analysis.** The server sees which seat posts, when, and roughly how long each message is (ciphertext length). It does not see content. Message padding and cover traffic are not implemented.
- **Metadata that remains.** The server knows room titles, seat pseudonyms, claimed roles, admission times and ledger entries, because those are the record the parties chose to keep. Facilitator and administrator emails are stored. Security events are kept with timestamps rounded to the hour.
- **Browser storage.** The session token and keys live in the tab's `sessionStorage`, scoped to the Diavanish origin, not in cookies or local storage. Closing the tab or signing out wipes them. Duplicating a tab copies them into the new tab. Anything with access to the tab (extensions, a compromised OS) can read them. Where `sessionStorage` is blocked, they stay in memory and a reload signs the tab out.
- **Translation runs on the device, or not at all.** Incoming chat can be shown in the reader's interface language using the browser's built-in Translator and LanguageDetector APIs (Chrome 138 and later). Translation happens only after a line is decrypted and its signature checked against the original text, and only for lines that verified (an unverified line is always shown as sent, so a forged line cannot gain polish from the translator); the translation is display-only and is never signed, sent or stored. Those APIs run a model the browser vendor ships to the device, and Diavanish only uses a model that is already downloaded, so no message text goes over the network. Diavanish never calls a server-side or cloud translation service, and there is no fallback to one: where the APIs or the model are missing, the original is shown with a one-time note. Two caveats remain: the reader trusts the browser vendor's on-device model and its implementation (as they already trust the browser), and a machine translation can be wrong, so every translated line keeps a "Show original" toggle.
- **Demo rooms are not end-to-end encrypted.** So that one person can try every role on one device, the server holds the demo room key. The interface labels this. Demos are off unless the operator sets `APERTURE_DEMO=1` (and, in production, `APERTURE_DEMO_IN_PRODUCTION=1`). Demo sessions are confined to demo rooms server-side, and the demo administrator can only read a demo-only view of the console.
- **Limited forward secrecy.** Anyone who later obtains an epoch's room key can read that epoch's captured ciphertext, up to 30 minutes of chat. Rotation runs only while the facilitator's tab is open, and participant tabs hold earlier epoch keys in memory until closed, so a compromised open tab still exposes its scrollback. There is no per-message ratchet.

## Out of scope

Compromised end-user devices, coerced participants, screenshots, and people repeating what they heard. Diavanish reduces what exists to be requested. It does not control what people do after they leave the room.
